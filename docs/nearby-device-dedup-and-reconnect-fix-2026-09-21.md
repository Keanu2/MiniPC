# 附近设备重复与聊天端反复重连问题记录

- 日期：2026-09-21
- 范围：`src/chat-end`、`src/model-end`
- 状态：代码修复完成；自动化测试通过；聊天端与算力端 HAP 构建通过；待三台真机回归

## 1. 问题现象

### 1.1 附近设备重复

算力端面板会重复显示“算力设备1”和“算力设备2”。同一台物理设备可能同时以三种身份进入列表：

1. 本机条目使用固定值 `self`；
2. 直连条目使用 LinkEnhance/BLE 当前连接的 `peerId`；
3. 其他算力端同步过来的集群条目使用发送方看到的 `id`。

BLE 私有地址会变化，`peerId` 也是连接级身份。原代码仅按这些临时 ID 去重，因此同一台机器在不同观察者眼中具有不同 ID，最终被当成多台设备。

### 1.2 聊天设备连接后断开并再次连接

本次日志采样中出现了以下链路：

```text
09:39:16 le-send failed code=32390206
09:39:52 le-send failed code=32390206
09:40:01 le-send failed code=32390206
服务端随后收到 disconnected reason=-425918060
重新连接后 peer MAC/peerId 发生变化
```

原代码把任意一次 `sendData()` 异常都解释为物理连接已经失效，立即执行 `drop(peer)`。页面层收到断开事件后固定等待 800 ms 再连接，而且没有次数上限，于是形成：

```mermaid
flowchart LR
  A[连接成功] --> B[周期性设备信息同步]
  B --> C[一次 sendData 异常]
  C --> D[立即 drop 连接]
  D --> E[800 ms 后自动连接]
  E --> A
```

这解释了“连接一会儿、断开、又重新连接”的循环，也会放大第一个问题：每次重新连接都可能得到新的临时地址和 `peerId`。

## 2. 根因

### 根因 A：展示 ID、连接 ID、设备身份混为一谈

- `self` 只在本机有意义，不是跨设备身份。
- BLE 地址和 LinkEnhance `peerId` 属于一次发现/连接，不能作为物理设备主键。
- `deviceInfoSync` 把本机、直连节点和转发节点合并，但原来的 `seen` 集合没有统一使用稳定主键。
- 两台算力设备可能使用相同公开名称，因此按名称去重也会误删真实设备。

### 根因 B：重复建链缺少双方一致的裁决规则

两台算力设备扫描到彼此后可能同时发起连接，形成两条相反方向的会话。原来的名称回退不能可靠地区分相同名称的设备，也没有在握手阶段用稳定身份合并两条会话。

### 根因 C：发送错误等同于断链

- 原 `write()` 捕获任何 `BusinessError` 后都调用 `drop(peer)`。
- 没有在调用前明确检查 `ArrayBuffer` 长度。
- 瞬时错误没有短暂重试。
- `deviceInfoSync` 与 `deviceInfo` 请求紧邻发送，增加控制消息突发。

### 根因 D：页面自动重连没有退避和上限

页面在每次断开后固定 800 ms 重试，成功连接后若很快再次触发发送错误，就会永久循环。应用退到后台时也缺少专门的重连门禁。

### 为什么原测试没有发现

- 重连用例让新旧连接报告相同 `peerId`，没有模拟 BLE 地址旋转。
- 没有覆盖“直连条目 + 远端 roster 条目 + 本机条目”的稳定身份合并。
- 没有覆盖 `sendData()` 抛出 `32390206` 时连接是否仍保持。
- 没有验证自动重连次数上限。

## 3. 解决方案

### 3.1 引入稳定安装身份 `deviceUid`

聊天端和算力端首次运行时生成 16 位随机安装 ID，存入 Preferences 的 `nearby-identity/installId`。重启不变，卸载重装后重新生成。该值只用于去重和建链裁决，不作为安全凭据。

协议的 `hello`、`hello_ack`、`deviceInfoSync.devices[]` 新增可选字段 `deviceUid`，保持对旧版本的兼容。协议校验限制其最大长度为 64。

### 3.2 统一设备列表主键

面板合并顺序统一使用：

1. `deviceUid`；
2. 旧版本没有 UID 时回退到 `id/peerId`；
3. 两者都没有时才回退到角色和公开名称。

本机、直连 peer、远端 roster 都进入同一个 `seen` 集合。`clusterSelfEntry()` 对外发送稳定 UID，不再把 `self` 当成跨设备 ID。

### 3.3 去除双向重复连接

BLE 广播携带稳定 UID 的短指纹，用于扫描阶段识别同一安装；握手仍交换完整 `deviceUid`。两台算力设备按身份排序，只允许排序较大的一方主动拨号。若竞态下仍形成两条连接，双方用相同规则保留规范方向的会话。

聊天设备重连时，算力端以完整 `deviceUid` 找到旧会话，用新连接替换旧连接，而不是新增一个设备。

### 3.4 发送队列防护

聊天端和算力端采用同样的发送策略：

- 继续按 peer 串行发送帧；
- 调用 `sendData()` 前拒绝空帧或超过 1024 字节的帧；
- 对可能的瞬时发送错误最多重试两次，间隔 120 ms、240 ms；
- `32390206` 最终失败时只让当前消息失败，不再据此销毁健康连接；
- 其他不可恢复错误仍断开连接，避免留下僵尸会话。

设备同步改为先发送完整 `deviceInfoSync`，队列完成后再请求该 peer 的 `deviceInfo`，避免同一侧连续交错控制消息。

### 3.5 有限退避重连

聊天端自动重连改为：

| 次数 | 等待时间 |
|---:|---:|
| 1 | 1.5 秒 |
| 2 | 4 秒 |
| 3 | 9 秒 |

三次仍失败后停止自动重连，显示“连接已中断，请点击‘连接’重试”。用户点击连接会重置计数。页面不在前台、正在推理、已有连接或已有连接任务时不会另起重连定时器；离开页面会清理定时器。

## 7. 兼容性与剩余风险

- 新旧版本可以连接，因为 `deviceUid` 是可选字段；但旧端没有稳定 UID 时只能采用临时 ID/名称回退，无法完全消除地址旋转造成的重复。因此三台设备应一起升级。
- 安装 UID 在卸载重装后会改变，这是预期行为；首次重连会被视为一个新安装。
- BLE 广播只携带 UID 的 32 位指纹以控制广播长度；握手后用完整 UID 二次确认，因此广播指纹碰撞不会直接合并已建立的连接。
- `deviceUid` 用于身份相关性而非鉴权；可信设备判断仍由现有同账号/超级终端设备列表完成。
- 当前结论已由代码、日志与自动化验证支持，最终无线稳定性仍以三机真机验收为准。

## 9. 第二轮真机反馈与修复

### 9.1 反馈现象

- 实际由算力设备1推理，但算力设备2的卡片错误显示“推理 1”。
- 任务标题显示“算力设备2 → 算力设备1”。
- 聊天设备断开后，其他算力端仍显示它在线。

### 9.2 根因

任务从聊天设备进入算力设备2，再由设备2转发给设备1时，设备1只知道上一跳连接是设备2。旧代码把任务的来源 `epoch` 同时用于“来源”和“执行者”计数，所以：

- 设备2被错误计为正在推理；
- 任务来源被错误显示为设备2，而不是最初的聊天设备。

离线聊天设备长期残留，是因为每台算力端把从其他算力端收到的 roster 再次转发。旧聊天条目会在算力端之间循环，即使最初的直连已经断开，也可能被另一台机器重新同步回来。

### 9.3 修复

- 转发请求新增可选 `origin` 字段，只传递“聊天设备N”这种公开标签。
- 任务卡的来源显示使用最终聊天来源，不再使用上一跳算力连接。
- 设备推理数只按 `workerEpoch` 统计；来源 epoch 不再算作执行任务。
- 对其他节点真实上报的 `modelRequests` 采用最大值补充，避免漏掉由其他协调机发起的任务，同时不与本机在途计数相加。
- 集群同步只发布本机和直连 peer，不再转发收到的远端 roster。
- 断开的 reporter 会立即从 `remoteSeen` 清除，并重新汇总在线聊天设备；检测到具体 epoch 已消失时立即发送一轮新的直连快照。

新增回归用例覆盖：上游协调机不显示为推理设备、最终聊天来源透传、断开 reporter 的聊天条目清理，以及远端 roster 不被再次转发。

### 9.4 当前连接与调度规则

聊天端目前并不保证全部连接算力设备1。它优先重连本次运行中已选择的稳定设备；没有已选设备时，自动连接信号最强的可信算力，手动连接时可以选择。

聊天端只需连接一个算力端。该节点作为本次请求的协调机，把本机和已连接的其他算力节点组成候选集；`pickNode` 优先选择当前请求数较少的节点，负载相同时优先可用内存更多的节点。若选中设备2，协调机会通过算力设备之间的 LinkEnhance 连接发送带 `sched=true` 的请求，因此聊天设备无需直接连接设备2。

## 10. 第三轮真机反馈与修复

### 10.1 任务创建时间

原生层已经在 `JobView.startedAt` 中提供毫秒时间戳，但 Web 仪表盘只渲染耗时、字数和首字时间，没有显示创建时间。本轮在任务卡元信息首位增加 `创建 MM-DD HH:mm:ss`；无法取得时间戳时显示“创建时间未知”。

### 10.2 附近设备排序

原列表按“本机、LinkEnhance peers 当前数组顺序、远端 roster 顺序”直接输出，因此连接先后会影响展示位置。现在发送 dashboard 事件前执行稳定排序：

1. 所有算力设备在聊天设备之前；
2. 算力设备按公开编号升序；
3. 聊天设备按公开编号升序；
4. 没有编号的兼容条目排在本组有编号条目之后，并以名称和稳定 ID 打破平局。

### 10.3 算力设备停用再启用后不组网

组网发现原来只有四次快速扫描。存活的算力端用完四次扫描预算后会永久停止扫描；如果重新启用的设备按稳定 UID 裁决不是主动拨号方，两边就都不会建立连接。另外，旧 `serverStopped` 回调可能晚于新 server 启动并误伤新会话。

修复包括：

- 算力 peer 断开时立即重置 mesh 发现预算；
- 四次启动扫描后仍每 30 秒保留一次低频发现，支持较晚重新上线；
- 重新启动 server 时重置发现时间；
- 停止 server 前先从 channel 脱离旧实例，忽略旧实例迟到的 `serverStopped` 回调，避免它关闭新 server；
- 页面重新启用近场后重新启动 mesh 和设备信息定时器。

新增回归用例覆盖任务创建时间、算力/聊天分组和编号排序、算力 peer 断开后换地址回归、server 停止后重新监听和广播，以及页面停用/启用后重新发起 mesh 发现。

## 11. 第四轮真机反馈与修复

### 11.1 停用再启用后自行断联、附近设备消失

第三轮已经处理“扫描预算耗尽”和旧 server 回调误伤新 server，但快速停用/启用仍有两个生命周期漏洞：

- `scanHits()` 注册的 BLE 扫描监听只能等超时自然结束。用户在 4.5 秒扫描窗口内停用近场时，旧扫描仍会在新服务启动后调用全局 `stopBLEScan()`，并可能把新一轮 mesh 标记为已经完成；
- 当前有效的 LinkEnhance server 若被系统异常停止，代码会关闭连接并提示重新启用，却不重建监听和广播。页面仍可能保留“近场已启用”的状态，但其他设备已经无法发现它。

本轮增加了可取消扫描和分代 mesh 运行标识：停用近场时立即停止旧 BLE 扫描、移除监听、使旧 Promise 收敛，并递增 mesh 运行代次。旧扫描的 `finally` 只有在代次仍匹配时才能修改 `meshBusy` 和 `meshSettled`，因此不会污染再次启用后的发现过程。

同时记录 server 的启用意图。主动停用仍会彻底取消恢复；只有当前 server 的真实 `serverStopped` 回调才保留启用意图，并按 0.8、2.5、7、15 秒退避自动重建 server 和 BLE 广播。`disconnect()` 在调用 `server.stop()` 前仍先脱离实例，所以主动停用产生的迟到回调不会触发自动恢复。

### 11.2 任务栏只显示本机实际执行的任务

协调节点转发任务时必须在内存中保留映射，才能把执行节点的流式回复转回原聊天设备；旧 dashboard 把这个内部协调记录也当作任务卡显示。因此同一个任务会同时出现在协调算力机和真正执行的算力机上，容易被理解为两台都在推理。

任务栏和顶部运行数现只包含 `workerEpoch === 0` 的记录，即由当前算力机实际提交给本机模型引擎的任务。转发给其他算力机的协调记录仍保留在路由器中用于回包和取消，但不再出现在本机任务栏。执行节点收到 `sched=true` 后创建的本地任务仍会正常显示，并保留原始“聊天设备N”来源。

新增回归用例覆盖：异常 server 停止后自动恢复监听与广播、扫描中停用后立即重新发现，以及协调任务从本机任务栏隐藏而本机执行任务继续显示。

## 12. 第五轮反馈：推理中断联与统一中心拓扑

### 12.1 现场证据和可确认范围

2026-09-21 14:53–14:55 的两台算力真机日志中，Mate 80 Pro 和 Mate 70 Pro 的算力间连接在同一秒分别记录 `le-disconnect reason=-425918060`，随后双方重新建链；日志中没有同一时段的 `le-send failed`。多次断开前后，两端还在周期性执行 4.5 秒 BLE 组网扫描，即使已经有算力连接和聊天连接。由此可以确认断开事件发生在 LinkEnhance 连接层、不是仪表盘单方面误报；仅凭该原因码和现有日志，不能断言由聊天设备、算力设备或系统无线栈哪一端发起。聊天设备当次日志未保留到可与算力日志关联的断开记录，仍需升级后的真机复测。

另一个明确的程序风险是：旧组网扫描每 30 秒继续运行，并且推理期间也会扫描。扫描与多条 LinkEnhance 流式发送同时使用无线资源，可能增加系统断链概率。本轮在任何本机执行或协调任务运行时立即取消扫描并暂停后续扫描；空闲时恢复。已有算力链路时的低频扫描间隔延长至 120 秒，断链后重置扫描预算以便重新发现。此举降低干扰，不等于承诺平台链路永不掉线。

应用切到后台时，现有 `EntryAbility.onBackground()` 会主动 `probe.cancel()` 并调用 `nearbyChannel.suspend()`；这会断开连接和停止推理。此行为没有被本轮改为后台持续运行，因此复测时应保持两端应用在前台、屏幕不锁定。若业务要求锁屏/后台持续推理，需要另行设计 HarmonyOS 后台任务与权限，不能把前台连接修复等同于后台保活。

### 12.2 中心节点规则

算力节点先通过近场发现和互连，按原有“可用内存优先、稳定身份打破平局”的规则形成公开编号。启动后留 10 秒选举窗口；扫描中看到另一台可信算力但尚未完成连接或内存上报时，不提前宣布自己为1。初始广播编号0用于算力互相发现，选举后才发布编号1/2。广播改号可能导致系统拆除现有 LinkEnhance 连接（旧日志曾有 `-425918059`），所以只在编号真正变化且没有在途任务时更新，不随每轮内存采样反复重启；选举期聊天端也不会连接编号0的节点。

稳定拓扑改为：

```text
聊天设备1 ─┐
聊天设备2 ─┼─ 算力设备1（唯一协调、通信中心） ─ 算力设备2（执行节点）
其他聊天设备 ┘                                  └─ 其他算力执行节点
```

- 聊天端只从广播编号 `slot=1` 的可信设备中选择；没有设备1时显示等待组网，不再按信号强度回退到设备2，也不提供手选设备2的入口。
- 算力设备2不接受普通聊天请求；设备1仍可向它发送 `sched=true` 的执行请求，结果按原链路经设备1回传聊天端。
- 编号确定后，非1号算力节点之间的连接会被清理，形成中心星型拓扑；计算节点断链后继续寻找设备1。
- 设备2与设备1短暂失联时保留设备2身份，不立即自升为第二个设备1；用户主动停用再启用近场会清除旧编号并重新选举。
- 当前只有设备1对外接收和调度新聊天任务。中心节点不可用时，新请求等待恢复，不绕过中心节点连接到其他算力机。
- 已连上中心的聊天端即便本机也有模型，新请求仍由设备1调度；本机模型只保留未连接中心时的离线兜底。

### 12.3 回归与待验收

## 13. 第六轮反馈：聊天设备自动/手动连接后仍断开

### 13.1 本轮真机证据

2026-09-21 19:37–19:40 读取当前接入的三台真机日志（算力80 Pro `017258256V003100`、算力70 Pro `53V0224C19002918`、聊天机 `53V0224C19002841`；另一台聊天机当时未接入 HDC）。算力设备1在 19:38:01、19:38:08 执行 4.5 秒 BLE 组网扫描；两条聊天连接分别在 19:38:06、19:38:08 报 `le-disconnect reason=-425918060`。即使没有正在执行的任务，旧代码只禁止“有任务时”扫描，没有禁止“已有聊天连接时”扫描。

同一轮日志中，算力设备1每 3 秒向每个 peer 发送一次完整 `deviceInfoSync`（当时每个 peer 占 2–3 帧），紧接着又发送 `deviceInfo`；两台聊天机和算力设备2都收到这一批后台消息。19:38:47–19:38:48 第二台聊天机发起请求时，算力设备1同时向三个 peer 发送 3 帧清单，随后该聊天连接在 19:38:48 断开，且算力设备1仍有 2 个在途任务。聊天机的对应日志约在 19:38:47 记录同一原因码。没有看到同时间的应用 `le-send failed` 或 `onBackground`。这证明断开不是聊天页单纯误显示，也没有证据表明应用主动调用断开；扫描/多帧状态同步与断链高度重叠，但系统原因码尚不足以证明唯一根因。

### 13.2 修改

- 算力中心有已就绪聊天连接时不再启动 BLE 组网扫描；若聊天握手完成时扫描已经开始，立即取消该扫描，旧扫描回调不能继续拨号或覆盖组网状态。推理期间禁扫规则保留。
- 已连上算力设备1的执行节点不再周期性扫描；新上线或断线的执行节点改为主动拨打已广播编号1的中心，不再受旧的设备名/身份排序方向限制。因此中心暂停扫描时，2号仍可主动加入或重连。
- 完整设备清单不再广播给聊天机，只发给算力节点；轮询周期由 3 秒改为 30 秒，并在存在本机任务时暂停清单和附带的状态请求。聊天机的正常请求、流式回复和显式服务准备消息不受影响。

这些改动是基于可复现的无线负载重叠做的减载修复，不宣称已经证明 HarmonyOS 底层断链原因。离线用例覆盖“聊天连接中取消/禁止扫描”“执行节点主动拨打1号”“清单不发聊天机、推理期间不发送”，全量 9 个测试文件通过。算力端 HAP 已重新编译成功，但仍未签名、未安装；需要用户安装后重新做四机实测。验收时分别连续保持空闲连接至少 10 分钟、同时进行两路长推理，观察 `le-disconnect` 是否消失；若仍出现，应保留四端相同时间段系统蓝牙日志与应用日志继续定位。

## 14. 第七轮反馈：状态滞后与1号停用后无法接管

本节替代第12节“2号失联后始终不自升”与第13节“全部设备信息30秒同步”的旧行为描述；前几轮记录保留作问题演变和回归依据。

### 14.1 原因

上一轮为压低无线负载，把完整 `deviceInfoSync` 连同小型 `deviceInfo` 状态请求一起降为每30秒一次；这确实会使内存、模型任务数和附近设备状态最长滞后约30秒。另一个逻辑是2号与1号断链后始终保留冻结编号，只有用户手动停用再启用近场才重选。聊天端只接受编号1的广播，因此旧1号真正关闭时，剩余2号仍广播2，聊天端不可能连上。聊天端原有自动重连只有三轮，且推理任务断线时 `activeId` 尚未清空，第一次重连调度被拦截，也可能在接管前耗尽重试。

### 14.2 本轮行为

- 设备内存和模型状态使用单帧 `deviceInfo` 每5秒请求一次，仅发往算力节点；本机推理路数发生变化时立即向算力节点推送。完整设备清单只在设备加入/退出、编号变化时立即同步，或每30秒保底同步一次；有在途任务时仍暂停全量清单，避免恢复之前的多帧拥塞。
- 2号与已确认的1号断链后继续扫描。至少15秒且连续三轮扫描均未发现仍在广播的原中心时，2号从冻结名单移除原1号，升为新1号并更新 BLE 编号广播。若旧中心仍可见，取消缺席计数并尝试重连，不因为一次无线抖动就接管。若新中心会话中原中心恢复，保留现任1号；原中心重新启用近场时可采用现任中心清单并成为执行节点。
- 聊天端仍只连接编号1，但自动重连扩展为最多五轮、逐步退避，以覆盖接管确认窗口；连接成功后清零重试次数。推理中链路断开时先结束该请求，再安排重连，不再被未清除的 `activeId` 拦住。

### 14.3 边界与验收

连续缺席扫描是两台算力设备场景下的保守故障判断，不是分布式共识：两台设备互相不可见但都仍在运行的极端无线分区，仍可能在确认窗口后短暂各自宣称1号。超过两台算力设备时，原2号优先接管；多重故障和网络分区仲裁尚未实现。已存在的推理任务不会跨旧中心自动续跑，断线任务会以错误结束，新请求才会经新中心调度。

本地测试新增：原中心广播仍在时禁止升号、连续三次缺席后升号并更新广播、恢复的原中心不会靠内存排名抢回中心、重新启动的旧中心采用新中心清单；状态轮询不会反复发送完整清单、成员变化立即触发清单；聊天端断线后重试覆盖接管窗口，推理中断后仍会安排重连。两端未签名 HAP 均编译成功。真机需四台都安装对应新版本，依次验证：先停用1号并保持2号近场启用，等待约20–35秒观察2号变为1号、两台聊天机重连；再重新启用旧1号，确认只存在一个1号；分别关闭原2号及现任1号复测。观察内存/任务数通常在5秒内更新，成员变化在链路事件后更新；所有步骤保存四端 `le-slot`、`le-hub failover`、`le-disconnect`、`connection` 同时段日志。
