# 聊天编号与中心故障接管修复记录（2026-09-22）

这份记录已经收进 [v0.4-hub](https://github.com/Keanu2/MiniPC/releases/tag/v0.4-hub)。2026-09-23 的[多算力接入审查](multi-compute-membership-review-2026-09-23.md)改写了本文第 9 节里「推理期间不发后台控制消息」：推理中如果成员变了，中心仍发送精简名单。现行行为以仓库 README 和那份审查为准。更早的 `nearby-device-dedup-and-reconnect-fix-2026-09-21.md` 已从仓库移除。编号以安装 UID 为准，接管按存活成员的旧排名。

## 1. 本轮问题与范围

用户反馈：

1. 两台聊天设备有时都显示「聊天设备1」。
2. 停用算力设备1后，其余算力不重新排序、不能找到新中心。
3. 有时原算力设备2已经显示为1，但聊天设备仍连接不上。

本轮在现有星型拓扑上修复，不改成聊天机随机直连执行节点。范围是源码、离线测试和本地记录；当时没有签名、安装，也没有改设备上的模型。按蓝牙名编号、只允许原 2 号接管，以及已接管节点无条件拒绝其他中心名单，都从这一轮起不再成立。

## 2. 证据与根因

### 2.1 编号把显示名称当成唯一身份

旧 `computeKey()` 优先返回蓝牙名，聊天编号也复用这个函数。两台同名手机落到同一个 key，`slotOf()` 自然返回同一个编号；本地和远端名单还混用了名称、`id:`、安装 UID 等不同键。单纯界面去重不能修复这种分配错误。

聊天端断线后保留自己的旧编号，页面又只接收非空标题，因此新中心重新分配1号后，尚未重连的另一台仍可能显示旧「聊天设备1」。此外，中心也会显示执行节点转发的旧聊天名单，进一步造成重复/在线假象。

### 2.2 接管判断与重新组网有遗漏

旧故障接管只允许 `selfComputeSlot === 2`，而且依赖特定断线路径提前设置计时；原2号不在或旧编号不一致时，其他存活设备无法接管。扫描达到启动次数后又被30秒退避限制。旧扫描将“启动失败后零结果”与真正完成的空扫描混在一起，既会拖慢恢复，也有误判风险。

旧远端名单按名称推断谁有权改号。显示名称相同、同一设备本地与远端 key 不同，都可能导致名单不生效。已稳定的中心在成员变化时也可能重新按内存排序，与维持现有中心的要求冲突。

### 2.3 显示升号，不代表广播与服务已恢复

两端扫描缓存只在新 `slot > oldSlot` 时更新，因此同一个扫描窗口先收到2号、后收到1号，缓存仍是2；聊天端又只拨1号，自然不会连接已经接管的设备。蓝牙地址切换时，还可能优先保留同一 UID 指纹的旧强信号地址。

算力端监听服务异常停止后的自动恢复会清空已选编号，并从0重新选举。更新广播遇到 `advertising === false` 又直接返回，可能让界面已是1号、无线侧却没有对应可连接状态。

### 2.4 本轮真机日志的结论边界

本轮只读取设备信息和已有日志，没有安装新版。可访问的原80 Pro算力日志在2026-09-22 15:02:01.990–15:02:02.000附近记录算力连接与两个聊天连接结束、`le-server closed`；一台聊天机在15:02:01.716记录 `-425918059`，之后15:02:03.224、15:02:16.886、15:02:31.892、15:02:51.900再次尝试准备连接，但所取窗口未见连接成功。

另一台原算力机当时没有接入 HDC，不能从这份日志确定其接管、广播和监听的真实状态，也不能凭原因码认定系统蓝牙断链的唯一原因。以上代码缺陷已用离线回归覆盖，但四机新版稳定性仍需实测。

## 3. 实现方案

### 3.1 唯一身份与聊天序号

- 算力排名统一优先使用安装 UID，握手、名单、掉线识别使用同一形式的身份键。显示名称不再合并同名设备。
- 聊天序号仅由当前中心为直接连接的聊天端分配；安装 UID 不同则序号不同。缺失 UID 时退回连接身份，不以蓝牙名合并。
- 同一近场服务会话保留已分配的聊天序号，短暂断线、MAC变化后用相同 UID 重连仍拿回原号，不挤占另一在线设备的号。因此离线后允许有编号空位。
- 停用/重启服务或切换中心后号码可以重新分配，不承诺永久编号；卸载或清除应用数据也会改变安装 UID。
- 聊天端断线后清空旧编号，标题回到「聊天设备」，直到新中心握手确认。
- 中心只展示自己的直接成员；执行节点只展示当前连接中心提供的间接成员。升为中心后立即忽略缓存的旧聊天名单。

### 3.2 故障接管与名单权威

- 任意已编号执行节点失去中心后继续发现；寻找中心期间不受启动四次扫描后的30秒节流限制。
- 至少15秒，且三次成功完成的扫描均未发现原中心/可信1号，才允许接管。被取消或启动失败的扫描不增加缺席次数。
- 按上一次排名保留当前可见的存活成员，排名最靠前者接管：原2号存在则优先；原2号也缺席时原3号等仍可接管。
- 已有中心维持自己的1号，不因新增设备内存更大就重新选中心。未编号节点从握手获知对端已是中心，可采用其中心身份。
- 名单按发送连接 epoch 找到实际设备 UID；仅当名单1号确实是发送者、包含本机、编号连续且身份不重复时更新排名。
- 两个曾经独立的中心重新相遇时，按稳定 UID 键顺序解决名单冲突。这是恢复收敛规则，不是网络分区下的多数派共识保证。

### 3.3 广播与监听恢复

- 有效算力广播中的编号始终取最新观测值，允许2→1，也允许1→2；仅含名称的扫描响应不能把有效编号覆盖为0。
- 聊天扫描按同一 UID 指纹的最新观测选择地址，避免旧MAC/旧编号因信号较强而遮住新中心。
- 本机编号变化时刷新广播；若当前没有广播则尝试启动，继续沿用已有广播失败退避机制。
- 系统异常停止监听后的自动恢复保留已选算力排名，再启动监听与相应编号广播；用户主动停用仍清空本地选举状态。

## 7. 明确边界

- 不是瞬时切换。15秒是最小故障确认时间，还要加扫描、发现、握手和重试时间；通常按约20–35秒观察，但不是时限保证。
- 无线扫描无法区分设备真的关闭与暂时不可见；多机/非对称无线分区仍可能暂时多中心。没有多数派仲裁，不能保证任意网络分区下全网唯一。
- 保留推理期间暂停扫描的减载规则；若旧任务迟迟不结束，接管会延后，需要结合任务取消日志判断。
- 旧中心上正在执行/转发的任务不自动迁移或续跑；断链任务结束后重新发送。
- 自动重连是有限重试，不是永久后台监控；应用切后台仍可能触发现有的近场暂停行为。
- UID用于区分安装身份，不是新的设备鉴权机制；沿用现有系统可信设备检查，本轮未扩大权限。

## 8. 接管后广播未真正上线（2026-09-22 续）

### 8.1 真机现象

停用算力设备1后，原2号界面会变成算力设备1，日志也有「广播启动」。聊天端随后多轮扫描（含手动重连）都扫不到算力广播，因此连不上新的1号。故障在广播刷新本身，不是聊天侧重试次数不够。

### 8.2 根因

改号路径调用了旧的无 ID `stopAdvertising()`，有时连停两次，然后立刻 `startAdvertising`，并把“调用没有抛异常”当成已经在播。系统停播是异步的：旧广播 ID 尚未释放时新的启动会返回成功，实际无线电上没有可扫描的 manufacturer 包。状态回调里的 STOPPED 若被当成意外掉线，还会再排队一次重试，和正在进行的改号启动互相抢。

### 8.3 修复

- 算力端改用返回 advertising ID 的异步启停；改号时只停自己持有的那条 ID，并等 `advertisingStateChange` 的 `STOPPED` 后再启动。
- 启动后必须看到 `STARTED`/`ENABLED` 才把 `advertising=true` 并打 `le-adv confirmed`。ID 返回但状态是 STOPPED/DISABLED，或超时无上线事件，不当成成功，走已有退避重试。
- 本轮主动停止的 ID 不会触发“意外停播重试”，以免把刚换上的 1 号广播又拆掉。
- 聊天端同一 MAC 后到的无名扫描响应不再把已经读到的 2→1 编号抹成 0。

### 8.4 验证

离线：`LinkEnhanceChannel.test.cjs` 覆盖停用途中多次刷新只停一次、晚到的旧 ID STOPPED 不影响新广播、启动结果返回前已 STOPPED、停用后迟到的 start 按 ID 清理、只返回 ID 没有 STARTED 不算成功。仓库内源码 `*.test.cjs` 全部通过。

真机请用同一批新 HAP：停用原1号，等原2号标题变为算力设备1后，看日志 `le-adv stopped` 后出现 `le-adv confirmed ... slot=1`，再在聊天端点连接。聊天扫描应出现 `le-scan ... slot=1`。

## 9. 设备卡片状态滞后

接管修复后界面可用，但内存、温度、CPU 仍显得慢。轻量 `deviceInfo` 每 5 秒才问一次对端，热档/电池/CPU 本地还缓存 4 秒，空闲时本机卡片也要等下一轮轮询才重绘。完整清单的 30 秒保底和推理期间停发多帧名单没有改：那是此前减载、避免和流式回复抢无线的边界。

本轮把 `DEVICE_INFO_POLL_MS` 改为 2000、`LOAD_CACHE_MS` 改为 1500，仍只向算力节点发单帧状态请求；成员变化立即发清单，否则 30 秒保底。当时有在途任务就不发后台控制消息。这一条在 2026-09-23 改过：推理中的成员变化仍发精简名单，完整遥测继续让路。空闲时卡片大约 2 秒内跟上对端采样。
