# Agent 耗时审查（2026-10-19）

审查阶段覆盖聊天端 ReAct、任务拆分、算力端调度及 GEWU 请求链路，未修改业务逻辑。下文“确认的问题”记录修复前状态；用户授权后的修改见末尾“后续修复”。证据包括源码、Pro S 保留的四条请求日志、实际代码的隔离复现和现有回归测试；不包含一次最新完整 Agent 任务的跨设备全程时间线，因此不能将某次用户任务的全部耗时精确归入某一阶段。

## 确认的问题

### 1. 文字拆分错误使用包含 VL 设备的集群数量

`apps/compute-node/entry/src/main/ets/cluster/DevicePool.ets:177` 的 `clusterLoad` 只检查 `ready`，不区分 `text`、`vision`。`InferenceRelay.load` 将该计数上报。聊天端 `ParallelTaskRunner.tryRun` 用 `load.idle >= 2` 决定是否尝试文字任务拆分，执行阶段又用 `load.total` 决定并发通道数。

只选 VL 的设备实际只上报 `vision`，不能承担这些文字子任务。隔离复现：一台 Pro 声明 `text`，一台 Pro S 声明 `vision`，两台空闲时计数上报 `idle=2,total=2`；文字可用设备只有一台，连续两个文字任务都选中了 Pro。这样会产生拆分和合并开销，却没有两台文字设备参与推理，并可能让同一台设备同时承担多个 GEWU 会话。

现场读取的 Pro S `model-selection.json` 当前选择 VL。该问题是手动选模后的遗漏联动，需要优先修复。建议为拆分提供按请求能力过滤后的设备计数；不能通过把 VL 虚报为文字能力来修复。

### 2. 工具完成后生成两次总结，最终复核并不读取草稿

聊天页面创建 `ReActAgentRunner` 时启用 `finalReview=true`；拆分模式的每个子任务也启用该选项。

`ReActAgentRunner.ets:350` 在收到工具后的 Final 草稿时设置 `reviewAttempted` 并继续模型循环。下一轮 `buildFinalReviewPrompt(task, activeEvidence)` 只接收原问题和工具证据，不接收草稿。这是独立重新生成完整答案；草稿仅在复核失败时作为备用内容保留。

对实际 runner 和 registry 的隔离复现：同一个单工具任务，关闭复核需两次模型调用，开启当前设置需三次。工具只执行一次，但模型经历“选择工具 → 总结草稿 → 独立重新总结”。建议保留完整性和证据校验，将工具后的综合收敛为一次；仅在校验发现具体缺项时触发额外修复。

### 3. 全量工具提示和变化的阶段前缀阻止有效复用

`ReActAgentRunner.buildHead` 默认携带全部工具描述、输入 schema、证据规则和技能目录；名称为 `compactPrompt` 的选项仍保留完整工具契约。工具返回后的 evidence 阶段再次附带全部工具定义。

Pro S 没有启用 `files/session-reuse.on`，因此当前 GEWU 请求不会使用已有的可复用会话。即使启用，该复用策略也要求 system 和任务头匹配；隔离复现确认首轮、证据阶段和最终复核的 system 不一致，不能靠打开开关直接复用这些阶段。

建议先缩小普通问题所需的提示和工具范围，再设计稳定的系统前缀及经验证的会话/KV 复用。保留被选工具的完整 schema 和权限规则，不删除必要约束。创建新会话并不等于已证明每轮重新读取全部权重，本次没有将两者混为一谈。

### 4. “整体超时”未覆盖全流程，过期后仍会发起合并

`ParallelTaskRunner` 的预算分别为拆分 60 秒、子任务阶段 300 秒、合并 120 秒。300 秒计时在拆分后启动，并在 `Promise.all(lanes)` 结束后清除；后续只要存在可用子任务结果，就进入新的合并模型调用，未检查 `timedOut` 或剩余总预算。

对实际 `ParallelTaskRunner` 注入缩放时钟和受控子任务，已复现 `totalDeadlineExpired=true` 后仍然调用 merge。配置预算因此可叠加到接近八分钟，取消和收尾还可能增加等待；300 秒不能作为全流程上限。建议以进入任务时创建的绝对截止时间约束拆分、子任务和合并，预算耗尽后直接返回已有结果。

不拆分 Agent 也只有十轮限制，没有整次任务的绝对时间预算；`InferenceClient` 的 170 秒是每一次模型请求的预算，不是整个 Agent 的预算。模型格式修复、工具循环和最终复核会累计耗时。

## 现场日志中的量化证据

来源为 Pro S 当天保留的 `gewu-chat.jsonl`，均使用 Qwen2.5-7B，`stream=false`、`max_tokens=2048`。

| 请求 | 输入大小 | system 字符 | 输出字符 | 提交至返回 |
| --- | ---: | ---: | ---: | ---: |
| Agent 形式请求 | 12,203 字节 | 10,696（15 个工具定义） | 34 | 30.285 秒 |
| 随后的短文本请求 | 97 字节 | 无 | 14 | 3.882 秒 |
| 随后的短文本请求 | 100 字节 | 无 | 23 | 4.143 秒 |
| 随后的短文本请求 | 103 字节 | 无 | 15 | 3.481 秒 |

这些不是控制变量基准测试：第一条与后三条存在冷/热状态和内容差异，不能将差值全归因于提示长度。它们能证明：Agent 形式请求在很短输出下仍耗时约 30 秒，输出长度不是唯一因素；约 12 KB 的请求输入及多轮重复处理值得优先优化。

当前 `LocalChat.buildRequest` 使用非流式请求，完整生成之前不会返回 token。这个选择还会增加用户感知的首字等待；过去已有 UTF-8 分块损坏记录，不能将直接打开流式视为已经验证的修复。

## 后续修复（2026-10-19）

用户授权后已修改聊天端和算力端：

1. `InferenceRelay.load` 按 `text` 能力过滤 Agent 拆分所需的设备计数；只选 VL 的设备不再抬高文字并发容量。设备列表仍展示实际在线设备。
2. 工具后的综合回答通过既有证据校验即返回，取消固定的第三次模型重写；只在校验发现具体问题时进行一次隔离修复。所需工具未执行时不会用纯总结替代执行，失败/空结果、结构化字段和权限校验继续保留。
3. 生产使用的紧凑提示去掉长示例、重复格式说明和执行器内部的证据规则清单；所有工具的描述、完整输入 schema 和约束保持可见。工具返回后继续提供本次观察和实际证据，综合阶段不再携带旧助手答案。保留全部工具可用性，未自动启用设备上的 `session-reuse.on`；NPU 会话/KV 复用仍需单独验证，不能将本次提示精简称为已经完成 KV 优化。
4. 进入任务时确定五分钟的绝对截止时间。拆分、子任务、合并及拆分失败后的单 Agent 回退共用剩余预算；合并仅能使用剩余时间。超时会返回已完成的结果，不再开启新推理；即使模型/工具忽略取消，外层等待仍会结束，迟到事件不能覆盖终态。模型返回后及工具派发前还有时钟检查，防止定时器因事件循环延迟尚未触发时执行迟到操作。
5. 新增 `[AgentTiming]` 阶段、输入字节和耗时日志，便于更新设备后区分执行、综合和按需修复的耗时，不记录原始提示或结果内容。
